V3 UPDATE NOTE:
The active website engine has been switched to `shift_engine_package_v3_day_first_reader/`.
The active production logic is day-first ReaderNumber based:
- ReaderNumber = 1 is Punch In.
- ReaderNumber = 2 is Punch Out.
- Punch In is the earliest same-day ReaderNumber 1.
- Punch Out first uses the latest same-day ReaderNumber 2 after Punch In, then falls back to later windows when needed.
- Required upload columns are EmpCode, TransactionDateTime, and ReaderNumber.
- The V3 engine creates the employee-date calendar itself and marks no same-day transaction as ABSENT.
- The backend must not add duplicate calendar completion rows for V3 output.

============================================================
1. PROJECT PURPOSE
============================================================

This project is a web application for predicting employee shifts from raw attendance transaction punch data. It can be run locally for development and is also deployed on Render for hosted use.

The main goal is:
- Upload raw transaction files from the attendance/access system.
- Use the existing production shift prediction engine.
- Predict employee shift/day status for each employee-date.
- Generate clean business CSV files and full debug CSV files.
- Compare generated predictions against attendance truth/answer-key files.
- Allow manual punch simulation for testing one employee/date scenario.

The app is built as a FastAPI backend with static HTML/CSS/JavaScript frontend pages. The active machine learning model and core inference logic live inside the shift_engine_package_v3_day_first_reader directory.

============================================================
12. CALENDAR COMPLETION BUSINESS LOGIC
============================================================

Service:
backend/services/calendar_completion_service.py

Purpose:
The shift engine only generates rows for employee-date combinations where transaction data exists. The backend adds missing employee-date rows so the output has a complete employee calendar for the uploaded transaction date range.

How date range is detected:
- Uses min and max TransactionDateTime from the uploaded transaction file.
- Dates are normalized to calendar days.

How employee list is detected:
- Uses unique EmpCode values from the transaction file.

Calendar generation:
- Creates every employee/date combination from start date to end date.
- Compares generated calendar keys against prediction rows.
- Missing keys are created as backend-generated rows.

Missing date rule:
- final_day_status = ABSENT
- final_shift = ABSENT
- shift_status = rule_generated
- final_status_label = ABSENT
- final_message = No transaction found; marked as absent
- row_source = backend_calendar_completion

Rows generated by the model get:
- row_source = model_prediction

Holiday handling:
- There is a HolidayProvider placeholder.
- Current implementation always returns False for holidays.
- No live holiday calendar is currently connected.

Important limitation:
- Calendar completion marks no-transaction days as ABSENT.
- It does not currently infer leave, public holidays, approved off-days, or other HR exceptions.

14. ENGINE DATA PREPARATION
============================================================

The engine requires:
- EmpCode
- TransactionDateTime

During preparation:
1. TransactionDateTime is parsed as datetime.
2. Invalid datetimes are removed.
3. EmpCode_norm is created from EmpCode as stripped string.
4. ReaderId, ReasonCode, TransactionCode are added as NaN if missing.
5. Rows are sorted by EmpCode_norm and TransactionDateTime.

The engine builds an employee transaction index containing:
- timestamp array
- timestamp integer nanosecond array
- timestamp text array
- reader values
- reason values
- transaction code values

For each employee/date:
- attendance_day is based on the transaction date normalized to midnight.
- The engine looks at punches from attendance_day to attendance_day + 48 hours.
- This supports normal shifts and overnight/next-day out punches.

============================================================
15. PUNCH PAIR CANDIDATE LOGIC
============================================================

For every employee/date window, the engine tries to find the best in-out pair candidate.

Candidate search:
- Uses all punches in the 48-hour window.
- For each known shift, checks whether a start punch falls within that shift start tolerance.
- Checks whether a later end punch falls within that shift end tolerance.
- Rejects spans shorter than min_valid_span.
- Rejects spans longer than max_valid_span.

Pair scoring considers:
- Difference from expected shift start time.
- Difference from expected shift end time.
- Difference from expected shift duration.
- Number of punches inside selected pair.
- Number of punches outside selected pair.
- Penalties for short/long invalid spans.
- Rewards for 3+ punches, close start, close end, and close duration.

Pair score formula concept:
- Lower score is better.
- start_diff is weighted.
- end_diff is weighted.
- duration_diff is weighted.
- outside punches add penalty.
- very good alignment subtracts reward.

If there is only one punch:
- The engine still creates weak single-punch candidates with large penalty.
- Business rules later withhold the result.

============================================================
17. FINAL SHIFT BUSINESS RULES
============================================================

The core final decision logic is in ShiftEngine.apply_business_rules.

Rule order matters. The first matching rule wins.

Rule 1: Sunday with transaction
- If is_sunday = 1:
  final_shift = WO
  final_day_status = WO
  shift_status = review
  final_status_label = WO_REVIEW
  final_message = Worked on weekly off / possible overtime or extra duty
  working_shift_hint = model prediction

Rule 2: Single punch
- If pair_single_punch_flag = 1:
  final_shift = unknown
  final_day_status = WITHHELD
  shift_status = withheld
  final_status_label = WITHHELD
  final_message = Only one transaction found
  working_shift_hint = model prediction

Rule 3: No valid in-out pair
- If valid_pair_found is false:
  final_shift = unknown
  final_day_status = WITHHELD
  shift_status = withheld
  final_status_label = WITHHELD
  final_message = No valid in-out pair found
  working_shift_hint = model prediction

Rule 4: Manual/continuous-like pattern
- If pair_manual_continuous_flag = 1:
  final_shift = model prediction
  final_day_status = WORKING
  shift_status = review
  final_status_label = SHIFT_REVIEW
  final_message = Continuous/manual-like pattern; review required
  working_shift_hint = model prediction

Rule 5: Very high model confidence
- If model confidence >= 0.995:
  final_shift = model prediction
  final_day_status = WORKING
  shift_status = predicted
  final_status_label = SHIFT_PREDICTED
  final_message = High-confidence shift prediction

Rule 6: Model and pair strongly agree
- If model confidence >= 0.98 and model prediction equals pair candidate:
  final_shift = model prediction
  final_day_status = WORKING
  shift_status = predicted
  final_status_label = SHIFT_PREDICTED
  final_message = Model and pair strongly agree

Rule 7: Overnight shift anchored by pair pattern
- If model prediction equals pair candidate
- and pair_next_day_flag = 1
- and start_diff <= 120
- and duration_diff <= 120
- and confidence >= 0.92:
  final_shift = model prediction
  final_day_status = WORKING
  shift_status = predicted
  final_status_label = SHIFT_PREDICTED
  final_message = Overnight shift anchored by pair pattern

Rule 8: Good-confidence prediction
- If confidence >= 0.95
- and pair candidate is missing, equals model prediction, or pair bucket is medium/unknown:
  final_shift = model prediction
  final_day_status = WORKING
  shift_status = predicted
  final_status_label = SHIFT_PREDICTED
  final_message = Good-confidence shift prediction

Rule 9: Model and pair agree but review suggested
- If confidence >= 0.85 and model prediction equals pair candidate:
  final_shift = model prediction
  final_day_status = WORKING
  shift_status = review
  final_status_label = SHIFT_REVIEW
  final_message = Model and pair agree; review suggested

Rule 10: Overtime-like pattern
- If pair_overtime_like_flag = 1 and confidence >= 0.80:
  final_shift = model prediction
  final_day_status = WORKING
  shift_status = review
  final_status_label = SHIFT_REVIEW
  final_message = Overtime-like pattern; review suggested

Rule 11: Low-confidence model output
- If confidence >= 0.75:
  final_shift = model prediction
  final_day_status = WORKING
  shift_status = review
  final_status_label = SHIFT_REVIEW
  final_message = Low-confidence model output; review suggested

Rule 12: Ambiguous row
- If none of the above apply:
  final_shift = unknown
  final_day_status = WITHHELD
  shift_status = withheld
  final_status_label = WITHHELD
  final_message = Ambiguous row

18. COMPARISON SERVICE BUSINESS LOGIC
============================================================

Service:
backend/services/comparison_service.py

Purpose:
Compare generated prediction output against attendance truth data.

Comparison flow:
1. Read prediction CSV.
2. Read attendance file.
3. Promote header row if needed.
4. Normalize prediction rows.
5. Normalize attendance rows.
6. Merge by employee_id and date using outer join.
7. Mark coverage differences.
8. Compare predicted shift vs normalized attendance shift family.
9. Build summary metrics.
10. Write full comparison CSV.
11. Write clean comparison CSV.
12. Return rows and summary to frontend.

Comparison key:
- employee_id
- date

Prediction normalization:
- employee_id from prediction employee aliases.
- date from prediction date aliases.
- predicted_final_shift from final_shift.
- predicted_final_status_label from final_status_label or shift_status/final_day_status aliases.
- predicted_final_day_status from final_day_status.
- transaction_first_in_time and transaction_last_out_time from punch columns or raw transaction text.
- predicted_shift_norm normalizes shift code.
- prediction_status_category is derived.
- prediction_shift_bucket is derived.

Attendance normalization:
- employee_id from attendance employee aliases.
- date from attendance date aliases.
- attendance_truth_shift from shift aliases.
- attendance_truth_status from status aliases.
- attendance_punch_in_time and attendance_punch_out_time from punch aliases.
- attendance_truth_shift_family is normalized.
- attendance_status_category is derived.

Deduplication:
- Duplicate employee/date rows are dropped, keeping the first row.

19. SHIFT NORMALIZATION AND ATTENDANCE FAMILY MAPPING
============================================================

General shift normalization:
- Converts value to uppercase.
- Empty, NULL, NAN, NONE, NAT, UNKNOWN become blank.
- If shift ends with W and the base shift is known, the W is removed.

Base shift codes:
- KFS
- KSS
- PF
- PGM
- PS
- PT

Attendance shift family mapping:
- PFW -> PF
- PF -> PF
- PSW -> PS
- PS -> PS
- PTW -> PT
- PT -> PT
- PG -> PGM
- PGM -> PGM
- PGW -> PGM

Non-working shift codes:
- WO
- OFF
- HOLIDAY
- LEAVE
- ABSENT

============================================================
20. COMPARISON RESULT TYPES
============================================================

Coverage results:

MISSING_IN_ATTENDANCE
- Prediction row exists but no matching attendance row exists.

MISSING_IN_PREDICTION
- Attendance row exists but no matching prediction row exists.

Shift comparison results:

MATCH
- Prediction and attendance answer key match.
- Used for hard predicted rows, not review rows.

SHIFT_MISMATCH
- Prediction and attendance answer key do not match.
- Used for hard predicted rows.

REVIEW_MATCH
- Review prediction matches attendance answer key.
- Kept separate from hard predicted matches.

REVIEW_MISMATCH
- Review prediction does not match attendance answer key.
- Kept separate from hard predicted mismatches.

NON_WORKING_EXCLUDED
- Row is excluded from shift accuracy because attendance truth is non-working or not comparable.

Mismatch reasons:
- no matching attendance row
- no matching prediction row
- prediction does not match attendance answer key
- review prediction does not match attendance answer key
- excluded non-working truth row

23. MANUAL PREDICTION LOGIC
============================================================

Manual prediction endpoint:
POST /api/manual-predict

Purpose:
Test one employee/date with supplied punch times without uploading a full file.

Input rules:
- employee_id is required.
- date is required and must parse as date.
- punch_in is required.
- punch_out is required.
- extra_punches are optional.
- extra_punches may be a list or comma/newline separated text.

Time parsing:
- Punch values may be time-only or full datetime.
- Time-only punches are attached to the selected attendance date.
- If punch_out is time-only and is earlier than punch_in, punch_out is moved to the next day.
- Extra time-only punches earlier than punch_in are moved to the next day.

Window rule:
- Uses the engine's window_hours_after value, currently 48 hours.
- At least two punches must be inside the attendance date window.

Manual transaction dataframe columns:
- EmpCode
- TransactionDateTime
- ReaderId
- ReasonCode
- TransactionCode

Employee history:
- After a normal prediction run, backend builds latest employee history from SHIFT_PREDICTED rows.
- It finds the most common final_shift per employee.
- It calculates confidence as top_count / support.
- A history is strong if support >= 3 and confidence >= 0.70.
- Manual prediction also looks for saved history artifacts:
  shift_engine_package/artifacts/employee_history.json
  shift_engine_package/artifacts/employee_shift_history.json
  shift_engine_package/artifacts/employee_history.csv
  shift_engine_package/artifacts/employee_shift_history.csv
  outputs/employee_history.json
  outputs/employee_shift_history.json
  outputs/employee_history.csv
  outputs/employee_shift_history.csv
